# 从一次请求开始，认识 AI 基础设施

你不需要先记住全景图里的所有项目。先抓住一个问题：**当你向模型发出一句话，到它开始回答，中间究竟是谁在工作？**

本文是新增的学习导读，不是原仓库文章的翻译。后面的完整译文保留原文结构；导读只负责搭桥，让你知道为什么读它。

## 先分清三个东西

把一套推理服务想成一间厨房：模型像一套已经学会的烹饪本领，推理引擎像真正按这套本领干活的厨师，平台像负责接单、安排人手和管理设备的运营系统。

这个比方只解释职责，不意味着模型真有人的理解方式。

| 你遇到的东西 | 它主要解决什么 | 不要混成什么 |
| --- | --- | --- |
| 模型 Model | 输入给定后，如何计算输出的概率等结果 | 不是整套对外服务 |
| 推理引擎 Inference engine | 高效执行模型计算，安排计算与显存使用 | 不等于管理整座集群的平台 |
| Kubernetes | 管理容器化工作负载，让它们落到节点上运行 | 不负责判断模型回答对不对 |
| CRI / containerd | 容器编排层和容器运行时之间的接口 / 运行容器的实现 | 不等于 Kubernetes 调度器 |
| KubeVirt | 在 Kubernetes 上管理虚拟机工作负载的项目 | 不等于普通 Pod 容器 |
| KWOK | 用来模拟 Kubernetes 节点和 Pod 行为的测试工具 | 不代表真实 GPU 性能 |
| Helm | 用 Chart 打包和安装 Kubernetes 应用的工具 | 不等于应用本身 |
| 推理平台 | 部署、路由、扩缩容、监控等服务管理 | 并不是又训练了一个模型 |

## 这条学习路线怎样走

1. 看[原仓库中文全景](../../../README.md)：先认识范围，不要求记住产品名。
2. 看[一次推理请求](./01-request.md)：理解 token、prefill、decode 和 KV cache。
3. 看[Pod 生命周期](../../../docs/kubernetes/pod-lifecycle.md)和[GPU Operator](../../../docs/kubernetes/nvidia-gpu-operator.md)：理解服务怎样真正运行。
4. 看[延迟与吞吐](./02-metrics.md)和[完整性能工具译文](../../../docs/inference/performance-testing.md)：理解“快”到底怎么量。
5. 看[缓存完整译文](../../../docs/inference/caching.md)：理解复用哪些计算、又占了什么资源。
6. 看[从组件到平台](./03-platform.md)及[AIBrix 译文](../../../docs/inference/aibrix.md)：把各层职责连起来。

## 怎样使用词卡

正文里有虚线提示的词可以点击。你可以先读一句话解释，再看本文含义。英语词卡把“单词平时的意思”和“这篇文章中的意思”分开。

遇到没有提示的英文，可以选中后查词；未收录时会明确提示，不会假装什么都懂。首版是精选词库，不是完整英语词典。

发音按钮调用当前浏览器的英语合成语音。它不是录制的真人音频，不保证所有设备都有英语语音，也不保证离线可用。

## 留心文章的身份

- **学习导读**：为你搭建概念顺序，不是全文翻译。
- **本批译文**：对应英文原文的完整翻译，保留源版本；尚未经过人工专业审校。
- **上游中文**：仓库原有中文，尚未全部逐句复核。
- **英文待翻译**：保留原文供检索，不计入已完成翻译。

“有文章”不等于“里面所有实验我们都跑过”。Issue 的研究计划、PR 的作者测试声明、我们的独立检查，是三种不同证据。

## 读完先试着回答

为什么一个模型能在电脑上运行，不代表它已经是一套可以供很多人稳定使用的服务？

只要能说出接入请求、安排资源、处理失败、观察运行状态中的几项，你已经开始把模型和基础设施分开了。
