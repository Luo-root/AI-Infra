# 延迟与吞吐：到底怎样才算快

本文是学习注释，不是性能工具文章的替代译文。下面数字是教学用的虚构示例，不是实测结果。

## 先看一个具体场景

你发出请求，2 秒后看到第一个 token。之后又过了 1 秒，收到了另外 50 个输出 token。

- **TTFT**（Time To First Token）：等到第一个 token 的时间。这个例子是 2 秒。
- **TPOT**（Time Per Output Token）：通常关注首个输出 token 之后，平均每个输出 token 的耗时。按这个简化例子，后续 50 个 token 用时 1 秒，平均是 20 毫秒。
- **ITL**（Inter-Token Latency）：相邻输出 token 之间的时间间隔。每个间隔不一定一样，不能仅凭平均值推断全部间隔。

具体工具对起止时间、首 token、流式数据块与 token 的统计定义可能不同。对照测试前要核对口径，不能看到相同缩写就直接横比。

## Throughput：同样时间做了多少工作

吞吐量可以按请求每秒（RPS）或 token 每秒（TPS）统计。还要说明是输入 token、输出 token，还是两者合计。

一辆大巴一小时能运很多人，不代表每位乘客都能马上出发。同样，整体吞吐高，不代表每个用户的等待时间都短。

增加并发可能提高设备利用率，也可能拉长排队时间。性能选型不能只挑一张“吞吐最高”的图。

## 为什么要看 P95 和 P99

假设 100 次请求里，95 次都很快，剩下 5 次等得很久。只看平均值，可能看不出那几位用户的糟糕体验。

P95、P99 是延迟分布的分位数，用来观察较慢请求。但不同采样量和计算方法会影响统计结果，也不保证下一次请求不超过它。

## 比较前固定这些条件

| 条件 | 为什么要说清 |
| --- | --- |
| 模型和精度 | 不同计算量不能当同一个实验 |
| 硬件、显存和网络 | 资源不同会改变瓶颈 |
| 输入长度、输出长度 | 长输入与长输出压的是不同部分 |
| 并发、请求速率和时间 | 低负载和排队拥堵不是一回事 |
| 预热与缓存是否命中 | 第一次加载不能和热缓存混为一谈 |
| 成功率和超时 | 不能把失败请求丢掉后宣称速度很快 |
